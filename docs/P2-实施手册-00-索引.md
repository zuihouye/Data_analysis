## 一、这套手册解决什么问题

把 7 个"返回 None → 500"的空壳接口 + 现有支付骨架，改造成真实可跑的业务链：

```
客户注册 → 浏览在售商品 → 下单 → 改数量 / 取消（未支付前）
        → 员工确认线下收款 → 已支付（冻结，不可改/不可取消）
```

同时补上三档角色的权限（客户 0 / 员工 1 / 管理员 2）与订单数据归属（防水平越权）。

## 四、先记住三句结论（面试用）

1. **删除 = 软删除**：外键约束（删客户会 1451）+ 订单是财务凭证 + RFM 分析口径要稳定，
   所以只改状态列，不物理 DELETE。
2. **金额 = 服务端算**：下单时把单价快照进 `orders.ppu`，`amount = ppu × quantity`；
   前端传来的 `ppu/amount` 一律忽略（页面上的金额只是预览）。
3. **状态推进 = 锁 + 条件 UPDATE**：Redis `order_lock` + `SELECT ... FOR UPDATE` +
   `UPDATE ... WHERE order_status = 旧状态`，用 `rowcount` 判断谁赢；输的一方返回 409。

## 五、必须知道的风险/边界

- **导入守卫会"锁住"演示库**：一旦注册过客户 / 下过单 / 手工加过商品，`/clear_input` 会拒绝全量导入（409）。
  演示前重置库的方法见 05 册 3.1；正确顺序是"新库 → 导入 CSV → 再产生业务数据"。
- **员工也能改商品**是你 2026-10-20 明确要求的（`staff_required`）；如果面试时想讲"更严格的权限分离"，
  把商品路由的装饰器换回 `admin_required` 即可，代码不用动。
- **依赖 MySQL + Redis**：集成测试与锁、幂等逻辑都要求两个服务在跑，否则测试会 skip/失败。
- **不做什么**（刻意范围边界）：真支付网关、退款、库存扣减、增量导入、审计日志表。
  面试时主动说清"没做 + 为什么 + 下一步"，比假装全做了可信。
