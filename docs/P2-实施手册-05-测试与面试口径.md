"""P2 集成测试：权限矩阵 / 客户下单 / 改单与取消 / 确认收款 / 软删除 / 导入守卫。

与 tests/test_import_db.py 一样的玩法：
  - 临时库 taobao_user_test，模块级 fixture 建库 → 跑 schema.sql → 导入真实 CSV → 跑完 DROP；
  - 所有 ops 测试都 monkeypatch utils.db.engine 指向临时库；
  - MySQL 不可用时整组 skip。

覆盖的核心安全性质：
  1. 未登录写操作 → 302 登录页；客户访问员工页 → 403；
  2. 客户只能看/改自己的订单（IDOR 修复）；
  3. 金额永远由服务端按数据库里的单价算，前端传什么都不影响；
  4. 已支付订单不可改、不可取消；确认收款重复执行返回 ALREADY_PAID；
  5. 删除全部是软删除，行还在、外键不炸；
  6. 系统里出现业务数据后，全量导入被拒绝（BusinessDataGuardError）。
"""

# ---------------------------------------------------------------- 建库工具

def _uri(database=''):
    auth = f'{Config.DB_USER}:{quote_plus(Config.DB_PASSWORD)}'
    return (f'mysql+pymysql://{auth}@{Config.DB_HOST}:{Config.DB_PORT}'
            f'/{database}?charset=utf8mb4')


def _statements():
    """读 schema.sql，去掉注释行，按分号拆成可执行语句"""
    lines = [ln for ln in SCHEMA_SQL.read_text(encoding='utf-8').splitlines()
             if not ln.strip().startswith('--')]
    return [s.strip() for s in '\n'.join(lines).split(';') if s.strip()]


def _count(engine, sql, **params):
    with engine.connect() as conn:
        return conn.execute(text(sql), params).scalar()


def _one(engine, sql, **params):
    with engine.connect() as conn:
        return conn.execute(text(sql), params).mappings().first()

def _login(client, phone, expect_location=None):
    """登录并返回轮换后的 CSRF token（登录成功会换 token，旧 token 立刻失效）。"""
    with client.session_transaction() as sess:
        sess['_csrf_token'] = CSRF_TOKEN
    resp = client.post('/login', data={'mobile': phone, 'pwd': PASSWORD,
                                       'csrf_token': CSRF_TOKEN})
    assert resp.status_code == 302, resp.get_data(as_text=True)
    if expect_location:
        assert expect_location in resp.headers['Location']
    with client.session_transaction() as sess:
        return sess['_csrf_token']

def test_customer_can_create_order_via_form(client, test_engine, accounts):
    token = _login(client, accounts['customer1_phone'])

    # 1. 打开下单页：服务端把一次性 token 写进 session
    assert client.get('/order/create').status_code == 200
    with client.session_transaction() as sess:
        form_token = sess['_order_form_token']

    before = _count(test_engine,
                    'SELECT COUNT(*) FROM orders WHERE customer_id = :c',
                    c=accounts['customer1'])
    # 2. 提交：故意把 ppu/amount/customer_id 也传上，验证服务端全部忽略
    resp = client.post('/order/create', data={
        'product_id': 'SKU-test-1', 'quantity': '3',
        'ppu': '0.01', 'amount': '0.01',
        'customer_id': accounts['customer2'],
        'form_token': form_token, 'csrf_token': token,
    })
    assert resp.status_code == 302 and '/order/list' in resp.headers['Location']

    after = _count(test_engine,
                   'SELECT COUNT(*) FROM orders WHERE customer_id = :c',
                   c=accounts['customer1'])
    assert after == before + 1

    order = _one(test_engine, 'SELECT * FROM orders WHERE customer_id = :c '
                              'ORDER BY order_id DESC LIMIT 1',
                 c=accounts['customer1'])
    assert order['customer_id'] == accounts['customer1']   # 归属来自 session
    assert order['quantity'] == 3
    assert order['ppu'] == Decimal('12.50')                # 单价来自数据库
    assert order['amount'] == Decimal('37.50')             # 金额由服务端算
    assert order['order_status'] == 1


def test_order_form_double_submit_only_creates_one(client, test_engine, accounts):
    token = _login(client, accounts['customer1_phone'])

## 4. 面试口径（华为 OD 项目深挖）

> 原则：每个问题都按"**问题 → 方案 → 为什么 → 验证**"回答，不要只背结论。
> 被打断时先给一句话结论，再展开。

### 4.1 一分钟项目介绍（背下来）

> "这是一个 Flask + MySQL + Redis 的电商订单后台。最初只有数据导入和 RFM 分析，我把订单链路补全成了完整业务闭环：客户自助注册登录、浏览商品、下单、修改数量、取消；员工确认线下收款后订单转为已支付。技术上重点做了四件事：RBAC 权限矩阵（客户/员工/管理员）、防水平越权（每个订单操作先校验归属）、Redis 锁 + 条件 UPDATE 的订单状态机（解决取消和确认收款的并发竞争）、以及全量数据导入的业务数据保护。测试是 pytest + 临时库，58 条原有 + 22 条新增。"

### 4.2 高频问题与参考回答

**Q1：为什么删除客户/商品/订单都用软删除？**
> 三个原因：① 外键约束——订单引用客户和商品，物理删除客户会报 1451；② 订单是财务凭证，数据要可追溯，不能消失；③ 分析口径稳定——RFM 依赖历史订单，删了就少数据。实现上直接用业务状态列（`cus_status=2`、`product_status=2`、`order_status=3`），没有再加 `is_deleted`，避免出现两个状态源。

**Q2：你说的"水平越权"具体是什么？怎么修的？**
> 就是 IDOR：用户登录了，但操作了不属于自己的资源。原来 `/pay/order`、`/pay/prepay`、`/pay/cancel` 只有 `@login_required`，客户 A 能取消客户 B 的订单。修法：在每个订单入口先做归属校验——客户只能访问 `customer_id == session.customer_id` 的订单，员工/管理员不限；不属于自己的统一返回 404 而不是 403，避免攻击者用状态码差异枚举订单 ID。列表页的数据隔离放在 SQL 层（`WHERE customer_id = :session值`），不是查出来再过滤。

**Q3：客户点取消和员工点确认收款同时发生，会怎样？**
> 可能两个请求都读到"待付款"，然后都去 UPDATE，后写的覆盖先写的，订单状态就错了。我们的做法：`order_lock(order_id)` 用 Redis `SET NX PX` 把同一订单串行化；事务内 `SELECT ... FOR UPDATE` 再兜一层；最后 `UPDATE ... WHERE order_status = 1`，用 `rowcount` 判断谁改到了。赢的改成功，输的拿到 0 行，返回"状态已变化，请刷新"。所以状态只会从 1 变成 2 或 3 其中一个。

**Q4：为什么用"条件 UPDATE + rowcount"，而不是先查后改？**
> "先查后改"中间有窗口——查完之后别人可能改了。条件 UPDATE 把"判断"和"修改"合成一条原子语句，数据库保证同一条 UPDATE 内状态判断和写入不会被打断；`rowcount` 是唯一可信的结果。这是乐观并发控制：不阻塞读，只在写时判断版本/状态。

**Q5：为什么订单里要存 `ppu` 快照，不直接关联商品价格？**
> 商品会调价，历史订单金额不能跟着变，否则对账对不上、财务凭证失真。所以下单时把当时单价复制进 `orders.ppu`，`amount = ppu × quantity`；改数量时也用快照价重算，而不是取商品当前价——否则"改数量"就变成"按新价重新下单"了。

**Q6：客户注册为什么要写两张表？**
> `customers` 是客户主数据（订单外键、RFM 都依赖），`users` 是登录凭据。上一版项目踩过坑：把密码放 customers，导入 CSV 时整表 DELETE 再 INSERT，密码就没了。所以必须分表，并且注册时两张表在**同一个事务**里写，避免"有客户没账号"或"账号引用悬空"。手机号重复靠 `UNIQUE` 约束兜底，捕获 `IntegrityError` 返回 409，因为应用层"先查后插"有并发窗口。

**Q7：导入功能原来有什么问题？你怎么保护的？**
> 原来 `/clear_input` 是全量快照导入：先 DELETE 三张表再 INSERT。有了客户账号后，问题有两个：① `users.customer_id` 外键会让 DELETE 报 1451；② 会把手工商品和网页订单一起删掉。我在 `write_to_db` 的 DELETE 之前加了一层守卫：只要发现 `role=0` 账号、非 `Customer-` 前缀客户、非 `PROD-` 前缀商品、非 `T` 前缀订单，就抛异常回滚，路由返回 409。长期正解是给表加 `source` 列做增量导入，但那是更大改造，本轮用 ID 前缀低成本实现同样效果。

**Q8：页面表单怎么防重复提交？**
> JSON 接口用现成的 `@idempotent`（要求 `X-Request-Id`，缓存 2xx JSON 响应）；但页面表单返回 302，不适用。所以下单用一次性 token：GET 渲染页面时生成 UUID 存 session，POST 校验后 `pop`，同一个 token 第二次提交会被拒绝。改数量和取消本身是幂等的（条件 UPDATE），重复点最多提示"状态已变化"。

**Q9：`order_id` 和 `transaction_id` 为什么两个 ID？**
> `order_id` 是数据库自增主键，内部操作/关联用；`transaction_id` 是对外业务流水号（唯一），展示、对账、对接支付网关用。对外暴露自增主键会泄露业务量，也容易被枚举。原代码的 bug 就是列表 SQL 没查 `order_id`、模板把 `transaction_id` 当主键传，导致订单操作找不到记录——这次一起修了。

**Q10：权限为什么用装饰器而不是在每个视图写 if？**
> 三个好处：① 权限声明和视图放一起，可读性高、漏挂明显；② 去重，`login_required`/`staff_required`/`admin_required` 各写一次；③ 改角色规则只改一处。每个装饰器自己处理"未登录"分支，避免装饰器叠加时的跳转顺序问题。另外菜单隐藏只是体验，**服务端装饰器才是安全边界**——面试官常追问这一点。

**Q11：为什么已支付订单不能取消？没有退款吗？**
> 当前阶段订单状态机是 1 待付款 → 2 已支付（终态）或 3 已取消，没有退款状态。已有支付文档里明确 P1-B（流水表、真网关、回调验签、退款）不做，所以已支付订单冻结。真实系统里会加 `4 退款中/5 已退款` 和退款单，且退款和支付一样要走状态机 + 幂等 + 对账。这里刻意不假装有退款，避免状态语义混乱。

**Q12：如果 QPS 上来，这套设计哪里会先撑不住？**
> 先说结论：当前是单机小项目，瓶颈不在代码而在 MySQL 单库和 Redis 单实例。真要扩：① 读多写少——订单列表加索引（已有 `idx_customer`）、加缓存；② 锁粒度已经是最小（按订单），但 Redis 锁要换成 Redisson/Redlock 或直接用数据库行锁；③ 写热点——订单表按用户/时间分库分表；④ 导入这种重操作改成异步任务（消息队列 + 任务状态）。另外，现在"确认收款"还可以用更简单的乐观锁版本号列代替 Redis 锁，但项目里锁+幂等已经作为支付骨架存在，订单操作复用它更一致。

**Q13：你这个改造的边界/没做什么？**
> 没做：真实支付网关与回调（P1-B 明确不做）、退款、库存扣减与超卖控制、增量导入/数据同步、审计日志表、管理员后台的批量操作、前端框架化（还是服务端渲染 + Bootstrap）。这些不是遗漏，是这一期明确的范围边界——面试时主动说清楚"哪些没做、为什么、下一步怎么做"，比假装什么都做了更可信。

**Q14：怎么证明这些功能是对的？**
> 自动化测试分两层：`test_import_db.py` 测导入/路由/CSRF/登录角色不被客户端篡改；`test_p2_crud.py` 覆盖权限矩阵、下单金额服务端计算、数据隔离（客户看不到别人订单）、改名/取消/确认收款的并发拒绝路径、软删除后行仍在、导入守卫回滚。测试用临时库，不碰真实数据，MySQL 不可用自动 skip。

**Q15：如果让你重做一次，会怎么改？**
> 会把"客户账号"从第一天就设计进去（数据模型：`users.customer_id` + `customers` 主数据分离），而不是等导入做了两轮才补；会给 Import 加 `source` 列和增量导入；会把业务层再抽一层 service（现在 `order_ops` 就是这个方向）；测试上会把"并发"用多线程/多进程真实压一次，而不只靠条件 UPDATE 的单测。

### 4.3 主动加分项（面试官不问也可以说）

- **数据生命周期**：CSV 导入 → 全量快照；Web 业务 → 增量数据；两者混用必须有保护。这是很多"学生项目"讲不出来的东西。
- **财务凭证意识**：订单不做物理删除、金额快照、确认收款留 `paid_at/paid_by` 审计字段。
- **失败路径设计**：`rowcount == 0`、409/404/405 的语义、一次性 token，都是"考虑过出错"的证明。
- **前后端安全分工**：前端算的金额只是预览，服务端永远重算；菜单隐藏不是权限。
