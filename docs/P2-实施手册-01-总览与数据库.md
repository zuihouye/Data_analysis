# P2 实施手册（一）：总览、业务规则与数据库改动

> 阅读顺序：**01 总览** → 02 认证与订单核心 → 03 页面路由与导入保护 → 04 模板代码 → 05 测试与面试口径。
> 配套文件：[`P2-migrate.sql`](./P2-migrate.sql)（已有库的迁移脚本）。
> 这份手册是给你**照着写进项目**的，代码都是完整可粘贴的；每一段都会说明"为什么这样做"，方便面试时讲。

---

## 0. 一句话目标

把 7 个"返回 None → 500"的空壳接口 + 现有支付骨架，改造成一条**真实能跑的业务链**：

```
客户自助注册 → 浏览在售商品 → 下单 → 改数量/取消（未支付前）
        → 员工确认线下收款 → 已支付（冻结：不可改、不可取消）
```

同时把权限从"登录就全通"改成**三档角色**：客户（0）/ 员工（1）/ 管理员（2）。

---

## 1. 最终业务规则（2026-10-20 确认版）

| 规则 | 说明 |
|---|---|
| 客户 = 纯买家（role=0） | 不是商家，没有"上架商品、卖货"概念；只能买 |
| 商品由内部人员维护 | **你最新要求：员工也能改商品** → 商品增/改/下架挂 `staff_required`（role 1/2 都行）。想收紧成仅管理员，把装饰器换成 `admin_required` 即可（一行） |
| 客户只能操作自己的订单 | 下单、改数量、取消都只认自己；员工/管理员可以操作任意订单 |
| 支付闭环 = B 方案 | 不接真实网关，`/pay/prepay` 仍返回 501（保留给面试讲"接口骨架"）；真实动作是**员工确认线下收款 → 订单 1→2** |
| 已支付订单冻结 | 不可改数量、不可取消；本阶段无退款（P1-B 已决定不做） |
| 删除全部是软删除 | 客户 `cus_status=2`、商品 `product_status=2`、订单 `order_status=3`；不物理 DELETE |
| 客户注册 | 同一事务里写 `customers`（主数据）+ `users`（登录账号，role=0），注册即登录 |
| 数据导入 | CSV 全量快照导入保留；但系统里有业务数据时**拒绝导入**（见第 5 节） |

## 2. 现状里必须知道的 5 件事（改代码前先看）

1. **7 个空壳**：`views/order.py` 的 `product_add/delete/update`、`order_update/delete` 和 `views/user.py` 的 `customer_update/delete` 都是 `return None` / `pass` → Flask 直接 500；而且路由没写 `methods`，默认只接受 **GET**，模板里用 `<a href>` 点一下就触发写操作，既不安全也不符合语义。
2. **认证只到"登录"**：
   - 7 个空壳**没有挂任何权限装饰器**；
   - `/customer/list`、`/ge_rfm` 只有 `@login_required`，客户登录后也能看全部客户和 RFM；
   - `/pay/order`、`/pay/prepay`、`/pay/cancel` 只有 `@login_required`，**任何登录用户都能操作任意订单**，这就是水平越权（IDOR），客户一上线就是事故。
3. **两个 ID 混用**：`order_list` 的 SQL 只查了 `o.transaction_id`，没查 `o.order_id`（`views/order.py:11-17`）；模板却把 `transaction_id` 当 `order_id` 传给 `/order/delete`（`templates/order_list_t.html:45`）。必须一起修。
4. **数据生命周期冲突**：`customers/products/orders` 来自 CSV，是**全量快照**（`/clear_input` 先 `DELETE` 再 `INSERT`）；`users` 是**增量数据**（只增改自己）。混用会冲掉密码或撞外键 1451 —— `schema.sql` 末尾已经记录过这个教训。
5. **支付骨架已经存在，要复用而不是重写**：Redis 锁 `order_lock(order_id)`、`@idempotent` 幂等装饰器、条件 UPDATE + `rowcount` 的状态机模式，都已在 `views/pay.py`、`utils/lock.py`、`utils/idempotent.py` 里。P2 只是在这套骨架上**多接一个入口**（页面表单）和**多推进一个方向**（1→2）。

## 3. 目标设计

### 3.1 角色与权限矩阵

| 动作 | 客户 role=0 | 员工 role=1 | 管理员 role=2 |
|---|---|---|---|
| 注册 / 登录 | 匿名可用 | — | — |
| `/product/list` 商品列表 | 只看在售 | 全部 | 全部 |
| `/product/add`、`/product/update`、`/product/delete` | ❌ 403 | ✅ | ✅ |
| `/customer/list`、`/customer/update` | ❌ 403 | ✅ | ✅ |
| `/customer/delete`（软注销） | ❌ | ❌ 403 | ✅ |
| `/order/create` 下单 | ✅（仅本人） | ❌ | ❌ |
| `/order/list` 订单列表 | 只看自己的 | 全部 | 全部 |
| `/order/update`、`/order/delete` | 仅本人未支付 | 任意未支付 | 任意未支付 |
| `/pay/confirm/<id>` 确认收款 | ❌ | ✅ | ✅ |
| `/pay/order/<id>`、`/pay/prepay`、`/pay/cancel` | 仅本人订单 | 任意 | 任意 |
| `/ge_rfm` RFM 分析 | ❌ 403 | ✅ | ✅ |
| `/clear_input` 导入数据 | ❌ | ❌ 403 | ✅ |

实现方式：三个装饰器，权限只写一次。

- `login_required`：登录即可（原有）；
- `staff_required`：role ∈ {1, 2}（新增）；
- `admin_required`：role == 2（原有）；
- `customer_required`：role == 0 且 session 里有 customer_id（新增，给下单用）。

> **面试话术**：认证解决"你是谁"，授权解决"你能干什么"。把授权做成装饰器有三点好处：① 权限声明和视图放在一起，一眼能看清；② 少写重复的 if，漏挂会很明显（打开文件就看到一堆没装饰器的写路由）；③ 以后加角色只改装饰器，所有视图自动生效。

### 3.2 订单状态机

```
                 客户下单
                    │
                    ▼
             ┌─────────────┐   员工确认收款（条件 UPDATE 1→2）   ┌─────────────┐
             │ 1 待付款    │ ─────────────────────────────────▶ │ 2 已支付    │
             └─────────────┘                                    └─────────────┘
                    │                                            冻结：不可改/取消
                    │ 客户/员工取消（条件 UPDATE 1→3）
                    ▼
             ┌─────────────┐
             │ 3 已取消    │
             └─────────────┘
```

**为什么 1→2 和 1→3 都必须带锁 + 条件 UPDATE**：

- 客户点"取消"和员工点"确认收款"可能同时发生。如果先 `SELECT` 出状态、再无条件 `UPDATE`，两边都会成功 —— 最后订单既"已支付"又"已取消"（后写覆盖先写）。
- 正确做法：`order_lock(order_id)` 串行化 + `UPDATE ... WHERE order_status = 1`，用 `rowcount` 判断谁赢了。输的一方拿到 0 行，返回"状态已变化，请刷新"。
- 这正是 `views/pay.py` 已有的模式，我们把它抽到 `utils/order_ops.py` 复用。

### 3.3 数据归属：只看 session，不看表单

- 登录成功时把 `role`、`customer_id` 一起放进 session（session 是 Flask 用 `SECRET_KEY` 签名的，客户端改不了）；
- 客户下单时，`customer_id` 一律取 `session['customer_id']`，**绝不读表单里的 customer_id**，否则改个请求就能替别人下单；
- 金额、单价一律从数据库读，前端传来的 `ppu`/`amount` 直接忽略；
- 客户查询自己的订单时 SQL 里加 `WHERE customer_id = session 里的值`。

### 3.4 为什么注册要同时写两张表

| 表 | 存什么 | 谁在用 |
|---|---|---|
| `customers` | 客户主数据（ID、地区、状态） | 订单外键、RFM 分析、"我的订单"归属 |
| `users` | 登录凭据（手机号、密码哈希、角色、customer_id） | 登录、权限 |

客户账户不存在 `customers` 里（历史教训：密码会被导入冲掉），也不能只存在 `users` 里（订单外键要求 customers 行存在）。所以注册流程是：

```text
一个事务:
  INSERT customers(customer_id='REG-xxxx', region, cus_status=1)
  INSERT users(phone, password_hash, role=0, customer_id='REG-xxxx')
 COMMIT → 自动登录
```

任何一步失败整体回滚，不会出现"有客户行但没账号"或反过来。

## 4. 数据库改动

### 4.1 `schema.sql` 要改两处

**① `orders` 表：在 `order_status` 后面加两列**（审计"谁确认的收款、什么时候"）：

```sql
    order_status   TINYINT UNSIGNED NOT NULL DEFAULT 1, -- 状态 1:已下单,2:已支付,3:已取消
    paid_at        DATETIME NULL,                       -- 线下收款确认时间
    paid_by        INT NULL,                            -- 确认收款的员工 users.id（审计用，不建外键）

    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers (customer_id),
    ...
```

**② `users` 表整段替换**（`schema.sql` 第 56~76 行那段）：

```sql
-- 4. 账号表：员工（role 1/2）+ 客户（role 0）
--
-- 为什么客户账号不放进 customers 表：
--   customers 来自 CSV 导入，是【全量快照】：/clear_input 会先 DELETE 再 INSERT；
--   账号是【增量数据】：只增、只改自己那一条。混在一起会冲掉密码。
-- 为什么 users.customer_id 建外键：
--   客户账号必须对应一条真实客户主数据（订单外键靠它）；
--   代价是导入前必须做保护（utils/loader.py 的 ensure_import_safe）。
CREATE TABLE IF NOT EXISTS users (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    phone         VARCHAR(32)  NOT NULL UNIQUE,        -- 手机号，登录标识
    username      VARCHAR(64)  NOT NULL,               -- 显示名
    password_hash VARCHAR(255) NOT NULL,               -- werkzeug.security 生成的哈希
    role          TINYINT UNSIGNED NOT NULL DEFAULT 1, -- 角色 0:客户,1:普通成员,2:管理员
    customer_id   VARCHAR(64)  NULL,                   -- 仅 role=0 的客户账号有值，员工为 NULL
    is_active     TINYINT UNSIGNED NOT NULL DEFAULT 1, -- 状态 1:启用,2:停用
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_users_customer (customer_id),
    CONSTRAINT fk_users_customer FOREIGN KEY (customer_id) REFERENCES customers (customer_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账号表（员工 + 客户）';
```

> **注意建表顺序**：`users` 在 `customers` 之后创建，外键才成立（现有 schema.sql 顺序正好满足）。
> **为什么 `orders.paid_by` 不建外键**：`orders` 建在 `users` 之前，建外键要么调表顺序要么写 ALTER；审计字段不值得引入这种顺序耦合。面试被问到可以答"可建，但会让 schema 顺序变脆"。

### 4.2 已有库怎么迁移

`CREATE TABLE IF NOT EXISTS` 对已存在的表**不会加列**。已有 `taobao_user` 库要执行 [`P2-migrate.sql`](./P2-migrate.sql)（或手动执行下面 SQL）：

```sql
USE taobao_user;

ALTER TABLE users
  MODIFY COLUMN role TINYINT UNSIGNED NOT NULL DEFAULT 1
      COMMENT '角色 0:客户,1:普通成员,2:管理员';

ALTER TABLE users
  ADD COLUMN customer_id VARCHAR(64) NULL
      COMMENT '仅 role=0 客户账号有值；员工为 NULL' AFTER role,
  ADD UNIQUE KEY uk_users_customer (customer_id),
  ADD CONSTRAINT fk_users_customer
      FOREIGN KEY (customer_id) REFERENCES customers (customer_id);

ALTER TABLE orders
  ADD COLUMN paid_at DATETIME NULL COMMENT '线下收款确认时间' AFTER order_status,
  ADD COLUMN paid_by INT NULL COMMENT '确认收款的员工 users.id（审计用）' AFTER paid_at;
```

验证：

```sql
SHOW CREATE TABLE users\G
SHOW CREATE TABLE orders\G
-- 应看到 uk_users_customer、fk_users_customer、paid_at、paid_by
```

### 4.3 为什么不做 `is_deleted`、不做 `source` 列

- **不加 `is_deleted`**：三张表本来就有状态列（`cus_status`/`product_status`/`order_status`），再叠一个删除标记就有两个状态源，所有查询都要同时判断，容易漏。软删除直接用语义最贴切的那一列。
- **不加 `source` 列**：区分"CSV 导入的数据"和"系统里产生的数据"的长期正解是加 `source` 列做增量导入，但那是 P1 级别的改造。本轮用 **ID 前缀**实现同样效果，零改表：

| 对象 | 系统生成规则 | CSV 导入数据（前缀） |
|---|---|---|
| 客户 | `REG-{uuid12}` | `Customer-190` |
| 商品 | `SKU-{时间戳}{随机}` | `PROD-006` |
| 订单 | `W{时间戳}{随机}` | `T000001` |

导入保护就是靠"有没有不符合 CSV 前缀的行"来判断该不该拒绝导入（见 5.3）。

### 4.4 索引/外键检查清单

- `users.customer_id`：`UNIQUE`（MySQL 允许多个 NULL，所以员工账号可以都为 NULL，不受唯一约束影响）。
- `orders`：已有 `idx_customer`，客户查自己订单走索引，不用加。
- `orders.customer_id → customers.customer_id` 外键：已有，这正是"不能物理删客户"的原因。

## 5. 导入保护（必做）

### 5.1 为什么必须做

给客户注册加完 `users.customer_id → customers` 外键后，**管理员再点一次"导入数据"**会发生：

1. `write_to_db` 先 `DELETE FROM customers`；
2. MySQL 发现 `users.customer_id` 还引用着这些客户 → **报 1451 Cannot delete or update a parent row**，整个导入失败（数据没丢，但功能坏了）；
3. 如果有人为了"修好"去关外键检查，就会把客户账号的引用删成悬空数据。

即使没有外键问题，全量重灌也会把系统里真实产生的**网页订单、手工商品**一起删掉 —— 它们是财务凭证/运营数据，不能丢。

### 5.2 实现位置

在 `utils/loader.py` 的 `write_to_db` 开头（**任何 DELETE 之前**、在调用方同一个事务里）加守卫：只要发现"CSV 之外的数据"，就抛异常回滚，`/clear_input` 返回 409 并说明原因。代码见 02 手册第 8 节。

### 5.3 判定 SQL

```sql
SELECT
  (SELECT COUNT(*) FROM users     WHERE role = 0)                          AS customer_accounts,
  (SELECT COUNT(*) FROM customers WHERE customer_id NOT LIKE 'Customer-%') AS web_customers,
  (SELECT COUNT(*) FROM products  WHERE product_id  NOT LIKE 'PROD-%')     AS manual_products,
  (SELECT COUNT(*) FROM orders    WHERE transaction_id NOT LIKE 'T%')      AS web_orders;
```

任何一项 > 0 → 拒绝导入。注意判断要放在**同一事务**里（`write_to_db` 收到的 `conn`），这样"检查 → 删除 → 写入"是一体的，不会出现检查通过后数据又被别人插进来的窗口（两个管理员同时操作的概率极低，但设计上要自洽）。

### 5.4 代价与正确操作顺序

- 代价：**第一次注册客户 / 第一次下单 / 第一次手工加商品之后，就不能再全量重灌数据了**。
- 演示/重置：直接换一个新库（`DROP DATABASE taobao_user_test` 或新库名），重新导入一次。
- 正确顺序（面试可讲"数据生命周期管理"）：**新库 → 管理员导入 CSV → 员工加商品/客户注册 → 业务数据产生；以后不再全量导入**。
- 长期正解：加 `source` 列 + 增量导入（UPSERT），或给导入加"仅导入历史区间"参数；这是后续迭代，不在 P2。

4. 未登录访问 7 个写接口 → 302 到登录页；GET 破坏性路由 → 405；缺 CSRF → 400。
5. 管理员在系统已有客户/订单后再点导入 → 409，且三张业务表数据一行没变。
6. 已支付订单不能再改、不能再取消。

## 9. 术语 / ID 规则速查

| 术语 | 含义 |
|---|---|
| 软删除 | 只改状态列，不删行；历史订单、外键、分析数据都不受影响 |
| ppu 快照 | 下单时把商品单价复制进 `orders.ppu`；以后商品调价不影响历史订单金额 |
| 水平越权 / IDOR | 有登录权限的用户操作了不属于自己的资源（如取消别人的订单） |
| 条件 UPDATE | `UPDATE ... WHERE order_status = 1`，用 `rowcount` 判断状态是否按预期变化 |
| 幂等 | 同一请求重复执行，结果一致；本项目 JSON 接口用 `@idempotent`，页面表单用一次性 token/状态机 |
| 导入守卫 | 检测系统内已有业务数据时拒绝全量导入，保护客户账号与财务订单 |

| 数据 | 系统生成 | CSV 导入 |
|---|---|---|
| 客户 ID | `REG-` + uuid 前 12 位 | `Customer-190` |
| 商品 ID | `SKU-` + 时间戳 + 随机 | `PROD-006` |
| 订单交易号 | `W` + 时间戳 + 随机 | `T000001` |
