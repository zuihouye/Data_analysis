## 1. 数据层加固

### 1.0 最终文件布局

数据层按「连接 / 判断 / 写入」三件事拆开，职责边界就写在函数签名里：

| 文件 | 职责 | 关键约束 |
|---|---|---|
| `utils/db.py` | 只管连接池 `engine` | 不含任何业务逻辑，15 行 |
| `utils/quality.py` | 清洗 + 校验（**只读**） | `clean()` 不删行；`validate()` 不修改 df |
| `utils/loader.py` | 写库 + 导入主流程 | `write_to_db()` 只用 DML，事务由调用方提供 |

**切分线**：`clean()` 只做类型转换、不删行；「该丢谁」由 `validate()` 判断、由 `process_and_import()` 执行。
把「判断」和「执行」分开，才能回答「删了多少、为什么删」。

**为什么不放进 `views/`**：视图层一旦持有 ETL，测试就必须 import Flask、CLI 和定时任务没法复用、
两个视图之间还会产生 import 依赖。判断标准很简单 —— **这段代码能不能在没有 HTTP 的情况下跑？能，它就不属于 views。**

**一处容易踩的坑**：`loader.py` 里必须写 `from utils import db` 再用 `db.engine`，
不能写 `from utils.db import engine`。后者会把 engine 绑死在 loader 的模块命名空间里，
测试的 `monkeypatch.setattr(utils.db, 'engine', 临时库)` 就打不到了 —— `test_clear_input_route_*`
两条用例正是在守这个约束。

**面试讲点**：分层不是为了目录好看，是为了可测性和复用性。`utils/quality.py` 能被 pytest 直接 import 测，
不需要 app context；`process_and_import(csv_path=..., db_engine=...)` 能被任何入口调用。

### 1.1 配置外置 —— 新建 `config.py`

```python
import os

class Config:
    DB_USER = os.getenv('DB_USER', 'root')
    DB_PASSWORD = os.getenv('DB_PASSWORD', '')      # 不要给默认值
    DB_HOST = os.getenv('DB_HOST', 'localhost')
    DB_PORT = os.getenv('DB_PORT', '3306')
    DB_NAME = os.getenv('DB_NAME', 'taobao_user')

    @classmethod
    def db_uri(cls):
        return (f"mysql+pymysql://{cls.DB_USER}:{cls.DB_PASSWORD}"
                f"@{cls.DB_HOST}:{cls.DB_PORT}/{cls.DB_NAME}?charset=utf8mb4")
```

再配一个 `.env`（**加进 `.gitignore`**）+ `.env.example`（提交，只有键没有值）。

**面试怎么讲**：12-Factor App 的 Config 原则 —— 配置属于环境，不属于代码。好处是同一份代码能在本地/测试/生产切换，凭据不随代码流转。

### 1.2 连接串字符集：`utf8` → `utf8mb4`

你现在的 `?charset=utf8` 是 MySQL 的**历史遗留别名**，实际只有 3 字节，存不了 emoji 和部分生僻字。
而你三张表是 `DEFAULT CHARSET=utf8mb4` —— **连接层和存储层不一致**。当前数据全 ASCII 所以没爆，一旦商品名里有 emoji 就会 `Incorrect string value: '\xF0\x9F...'`。

改成 `utf8mb4` 即可。这是个很好的「细节意识」素材。

### 1.3 去重键用错了列

现在（旧 `db.py:39`）：
```python
customers_df = df[['Customer ID','Region']].drop_duplicates(subset=['Customer ID','Region'])
```

但 `customers.customer_id` 是**单列主键**。所以「同一客户出现在两个地区」会生成两行同 `customer_id` → 主键冲突，整批导入失败。

修法是把两个动作**分开**：冲突检测归 `validate()`（只报告），去重归 `write_to_db()`（只执行）。

```python
# validate() 里：只报告，不改数据
add_warning('customer_region_conflict',
            df.groupby('customer_id')['region'].transform('nunique') > 1,
            '同一客户出现在多个地区（customers.customer_id 是主键，会冲突）',
            ['customer_id', 'region'])

# write_to_db() 里：按主键单列去重
customers_df = df[['customer_id', 'region']].drop_duplicates(subset=['customer_id'])
```

**面试怎么讲（重点）**：数据清洗遇到冲突有四种策略 —— 静默丢弃、保留首个并告警、人工介入、直接失败。**选哪种取决于业务后果**。客户地区冲突会影响地区维度的分析准确性，所以我选择「保留首个 + 在报告里告警」，而不是静默吞掉。这个「不静默」的意识是加分项。

### 1.4 真正的原子性 ★ 最重要的一处

> **当前代码已经采用本节方案 ①**：`utils/loader.py` 的 `write_to_db()` 只用 DML，
> `process_and_import()` 用 `with (db_engine or db.engine).begin()` 包住整个写入；
> 回归测试见 `test_failure_inside_transaction_rolls_back`、`test_import_preserves_schema`。
> 下面先回顾改造前的问题，再说明当前方案。

**改造前的问题**（早期版本，当前已修复）：
```python
with engine.begin() as conn:      # ← 事务块
    conn.execute(text("SET FOREIGN_KEY_CHECKS = 0;"))
    conn.execute(text("TRUNCATE TABLE orders;"))      # ← DDL，隐式提交！
    ...
customers_df.to_sql('customers', engine, ...)   # ← 块外，自己新开连接
products_df.to_sql('products', engine, ...)     # ← 块外
orders_df.to_sql('orders', engine, ...)         # ← 块外
```

**两个独立的致命问题：**

**(a) `TRUNCATE` 无法回滚。** 我实测确认：

```
插入 3 行 → with engine.begin() 里 TRUNCATE → 抛异常触发回滚 → 剩余 0 行
对照组：插入 3 行 → with engine.begin() 里 DELETE   → 抛异常触发回滚 → 剩余 3 行
```
`TRUNCATE` 是 DDL，会**强制隐式提交**，所以 `with engine.begin()` 根本保护不了它。

**(b) `to_sql` 用的是新连接。** 传 `engine` 时 pandas 自己借连接、自己提交。所以三条 `to_sql` 各自独立，互不构成事务。

**净效果：只要 `customers.to_sql` 之后任何一步失败，三张表已经被清空了，没有任何回滚，四个页面全空。**

---

**核心原则先说清楚：写库只用 DML，不碰任何 DDL。**
`CREATE` / `TRUNCATE` / `RENAME` 都会**隐式提交**，一旦混进 `with engine.begin()`，事务保护就是假的。

### ① 推荐：全用 `DELETE` + `to_sql(append)`，整个写入一个事务 ★

```python
def write_to_db(df, conn):
    customers_df = df[['customer_id', 'region']].drop_duplicates(subset=['customer_id'])
    products_df  = df[['product_id', 'product_name', 'product_category', 'ppu']] \
                     .drop_duplicates(subset=['product_id'])
    orders_df    = df[['transaction_id', 'order_date', 'customer_id',
                       'product_id', 'quantity', 'ppu', 'amount']]

    # 按依赖顺序删：先子表 orders，再父表 —— 所以不需要关 FOREIGN_KEY_CHECKS
    for t in ('orders', 'customers', 'products'):
        conn.execute(text(f'DELETE FROM {t}'))

    # 按依赖顺序写：先父表后子表，否则外键校验失败
    customers_df.to_sql('customers', conn, if_exists='append', index=False)
    products_df.to_sql('products',   conn, if_exists='append', index=False)
    orders_df.to_sql('orders',       conn, if_exists='append', index=False)


with (db_engine or db.engine).begin() as conn:   # 整个写入是一个事务
    write_to_db(df, conn)
```

`db_engine` 参数只用于测试时指向临时库；生产路径走 `db.engine`。

> **关键知识点 1**：`to_sql` 的第二个参数不只能是 `engine`，也可以传 `Connection`；传 `Connection` 时它不自己提交，由外层事务控制。我实测验证过：传 `conn` 后中间抛异常，插入的行确实被回滚了。
>
> **关键知识点 2**：删除顺序安排好（子表先删），就**完全不需要 `SET FOREIGN_KEY_CHECKS = 0`**。那个开关是 **session 级**的，一旦中间抛异常，恢复语句不会执行，连接归还连接池后**外键检查还是关闭的**，静默失去保护 —— 这是个很隐蔽的 bug。
>
> **关键知识点 3**：InnoDB 的 MVCC 让并发**读**不受影响（读的是旧快照），只有并发**写**会被 DELETE 的锁挡住。所以「DELETE 会锁表所以不如换名」这个直觉，在读多写少的场景下并不成立。

实测结果（V2 数据，2000 行）：写入后 812 客户 / 10 商品 / 1999 订单（校验丢弃 1 行业务级重复）；
主键、`UNIQUE`、3 个索引、2 个外键、`DECIMAL` 精度**全部原样保留**；
事务中途抛异常 → **失败前 1999 行，失败后 1999 行**，完整回滚。

### ② 进阶：临时表 + `RENAME TABLE` 原子换名（真需要不停机时才用）

**⚠️ 这里有个极容易踩的坑，我实际验证过：**

```python
# ❌ 错误写法
customers_df.to_sql('customers_new', conn, if_exists='replace', index=False)
conn.execute(text("RENAME TABLE customers TO customers_old, customers_new TO customers"))
```

`to_sql(if_exists='replace')` 的内部行为是 **`DROP TABLE` + `CREATE TABLE`**，而建表是**按 DataFrame 的 dtype 推断列类型**的。
pandas 的 dtype 体系（`int64` / `float64` / `datetime64` / `object`）根本表达不了 MySQL 的 schema。

我实测对比「换名后」的 `orders` 表：

| | 改造前 | 换名后 |
|---|---|---|
| `order_id` | `bigint NOT NULL AUTO_INCREMENT` | **没了** |
| `order_date` | `date NOT NULL` | `datetime DEFAULT NULL` |
| `quantity` | `int(11) NOT NULL` | `bigint(20) DEFAULT NULL` |
| `ppu` / `amount` | `decimal(10,2)` / `decimal(12,2)` | **类型被改写** |
| `PRIMARY KEY` | 有 | **没了** |
| `UNIQUE KEY transaction_id` | 有 | **没了** |
| 3 个索引 | 有 | **没了** |
| 2 个外键 | 有 | **没了** |

更直接的证据：换名后往新表插一条**重复的** `transaction_id`，**插入成功了** —— 唯一约束已经消失。

**正确写法**：用 `CREATE TABLE ... LIKE` 复制结构，再用 `if_exists='append'`：

```python
conn.execute(text("CREATE TABLE customers_new LIKE customers"))
conn.execute(text("CREATE TABLE products_new  LIKE products"))
conn.execute(text("CREATE TABLE orders_new    LIKE orders"))
customers_df.to_sql('customers_new', conn, if_exists='append', index=False)
products_df.to_sql('products_new',   conn, if_exists='append', index=False)
orders_df.to_sql('orders_new',       conn, if_exists='append', index=False)
conn.execute(text("""
    RENAME TABLE customers TO customers_old, customers_new TO customers,
                 products  TO products_old,  products_new  TO products,
                 orders    TO orders_old,    orders_new    TO orders
"""))
```

两点必须知道：
1. `CREATE TABLE ... LIKE` **只复制列定义、主键和索引，不复制外键约束** —— 换名后要手动 `ALTER TABLE ... ADD CONSTRAINT` 补回来；
2. `CREATE TABLE` 和 `RENAME TABLE` 都是 DDL、都隐式提交，所以外面那层 `engine.begin()` **不是真事务**。这个方案真正的保证是「**正式表要么全不变，要么被一个原子的 `RENAME` 一起换掉**」，而不是「能回滚」。说清楚这个区别，比说「我有事务保护」有说服力得多。

> 2000～30000 行的数据量，方案 ① 的 `DELETE` 是毫秒级，换名那套复杂度换不到任何实际收益。**用 ① 就够了**，② 留着回答「如果要不停机导入怎么办」。

### ③ 不要做：`TRUNCATE` 放进事务里

`TRUNCATE` 是 DDL、强制隐式提交，`with engine.begin()` 根本保护不了它。我实测：
```
插入 3 行 → begin() 里 TRUNCATE → 抛异常 → 剩余 0 行   ← 回滚失败
插入 3 行 → begin() 里 DELETE   → 抛异常 → 剩余 3 行   ← 回滚成功
```

**面试怎么讲（这是你最强的技术故事之一）**：
> "我原本用 `with engine.begin()` 包住清表操作，以为有事务保护。后来意识到 `TRUNCATE` 是 DDL、会隐式提交，而且 `to_sql` 传 `engine` 时是独立连接，所以这个事务其实是假的 —— 导入中途失败会留下空库。
>
> 我实测验证了这一点。接着我想用『灌临时表 + `RENAME` 原子换名』解决，还特意克隆了一套结构相同的表跑完整流程、再 `SHOW CREATE TABLE` 对比 —— **结果发现换名后新表的主键、唯一键、三个索引、两个外键全丢了，列类型也被改写**。根因是 `to_sql(if_exists='replace')` 会按 DataFrame 的 dtype 重建表。我还验证了换名后重复的交易号能插进去。
>
> 最后我改成『单事务 `DELETE` + `to_sql(append)`』：表结构一行不动，失败实测能完整回滚，重复交易号仍被 `UNIQUE` 拦住。我也顺手去掉了 `SET FOREIGN_KEY_CHECKS = 0` —— 那个开关是 session 级的，异常时不恢复会污染连接池。"

这个故事包含了：**框架误用 → 主动验证 → 踩坑并定位根因 → 方案权衡 → 二次验证**。比背八股强得多。

### 1.4.1 顺带补上：把表结构写进仓库

改造前**建表 DDL 完全不在仓库里**，别人 clone 下来无法建库，面试官也没法复现。
补一个 [`schema.sql`](../schema.sql)，只含 `CREATE TABLE`（不含 `CREATE DATABASE` / `USE`），
这样它可以被执行到任意一个已选定的数据库里 —— 集成测试就是用它在临时库上建表的。

### 1.5 加数据质量校验

新增 `validate(df, dedupe_business_duplicates=True)`，**在写库之前**跑，返回 `(report, drop_mask)`。

**关键设计：`validate()` 只检查、不修改 df。** 该丢谁由 `validate()` 判断、由 `process_and_import()` 执行 —— 这样「删了多少、为什么删」才可追溯。
所以 `clean()` 也必须**只做类型转换、不删任何行**（不能有 `dropna()`）。这条边界一开始就要划清楚，否则「清洗」会变成一个什么都干的筐。

| 检查 | 严重级 | 方法 | 为什么 |
|---|---|---|---|
| 必填列存在 | **fatal** | 比对列名集合 | 缺列后面全无意义，直接短路 |
| 空值 | error | `isna().any(axis=1)` | 对应数据库 `NOT NULL` 列 |
| 交易号重复 | error | `duplicated(keep='first')` | `transaction_id` 是 UNIQUE，重复会整批失败 |
| **业务级重复** | error | `duplicated(subset=[客户,日期,商品,数量,单价,金额])` | **UNIQUE 拦不住**：交易号不同、内容完全相同，会静默重复计算金额 |
| `Amount == Quantity × PPU` | error | `np.isclose(a, q*p, rtol=1e-6)` | 数据集 README 明确要求校验；无法推断哪个值对，绝不能自动修 |
| 非正数 | error | `<= 0` | 业务上不合法 |
| 未来日期 | warning | `> today` | 可能是预付订单或时钟错误 |
| 客户-地区一对多 | warning | `nunique() > 1` | 主键冲突隐患 |
| 离群值 | warning | IQR 1.5 倍 | **只警告、绝不丢弃** —— 业务上无法自动判断它是不是脏数据 |

三个面试讲点：

1. **浮点比较必须用 `np.isclose` 而不是 `==`**。但还有一层：`np.isclose(nan, x)` 返回 `False`，所以必须先用一个 `comparable = expected.notna() & amount.notna()` 掩码把它挡掉，否则空值行会被误报成「金额不一致」。
2. **严重级要分层，fatal 必须短路**。列都缺了还去跑金额校验，只会得到一堆连锁的假错误。
3. **离群值用 IQR 而不是 3σ**。因为均值和标准差**本身就会被离群值污染** —— 一个极端值能把 σ 抬高到把所有异常都盖住。

**`dedupe_business_duplicates` 是业务策略，不是技术判断。** 同一份数据，这个开关决定它是 error（丢弃）还是 warning（保留）—— 因为「同客户同天同商品同金额是否算重复」取决于业务，不取决于代码。把它做成参数而不是写死，是这条的关键。

**还有个反面教训：高误报率的检查比没有检查更糟。** 我一开始加了「同客户同天同商品」的 error 级检查，实测在 30000 行数据上**命中 7187 行（23.96%）** —— 那显然是真实复购行为，不是脏数据。于是降级成 warning。一个天天报假警的检查，最后会被所有人忽略。

**返回一份报告**（而不是只返回 df）：
```python
{
  'total': 2000, 'valid': 1999, 'dropped': 1, 'drop_index': [...],
  'fatal':    [],                                        # 非空 => 拒绝整个导入
  'errors':   [{'check': 'business_duplicate', 'count': 1, 'rate': 0.0005,
                'detail': '...', 'samples': [...]}],
  'warnings': [{'check': 'amount_outlier', 'count': 272, ...}],
}
```
`drop_index` 和 `drop_mask` 是同一份信息的两种形式，**必须一致**（有测试锁这一点），否则调用方会按错的集合过滤。

**还有一道阈值保护**（`max_drop_rate=0.2`）：脏数据占比超过 20% 就**整体拒绝导入**，而不是「导进去 80%」。
因为脏数据这么多通常意味着**文件拿错了或格式变了**，不是数据本身脏。这个判断只有放在 `process_and_import()` 里才对 —— 它是导入策略，不是行级质量判断。

让 `/clear_input` 把报告返给前端。**面试讲点**：这是「数据质量守门人」模式 —— 脏数据不进库比进库后再洗便宜得多。

## 2. 路由层

### 2.1 `/clear_input` 已从 GET 核按钮改成 POST ✅

**已落地的修复**：
1. `clear_input.py` 声明 `methods=['POST']`
2. `layout_t.html` 把 `<a href="/clear_input">` 改成 `<form method="post">` + 按钮
3. `tests/test_import_db.py` 里两条路由测试同步改成 `.post('/clear_input')`

**为什么必须这么改**：HTTP 语义中 GET 必须是 **safe**（不改变服务端状态）且 **idempotent**。

另外 GET 型写操作无法使用常规 CSRF Token 防护，因为它可以被 `<img src="...">` 跨站触发。

**安全层（2026-10-19 已补齐，见 `views/auth.py`）**：
1. ✅ `@admin_required` —— 未登录 302 跳 `/login?next=...`，普通成员 403（认证 + 授权分开）
2. ✅ CSRF Token —— `before_app_request` 对所有 POST/PUT/PATCH/DELETE 统一校验（`csrf_token` 表单域 / `X-CSRF-Token` 头）
3. ⬜ 前端二次确认 —— 点击即执行清空重灌，手滑仍会触发（体验优化，不是安全边界）
4. ✅ 权限粒度 —— 已限制为管理员

**面试讲法**：这是一个完整的「识别风险 → 修改 HTTP 动词 → 同步前端 → 同步测试 → 再补认证/授权/CSRF」的过程。
能主动说「POST 只是解决了 GET 的 safe 语义问题，不等于安全」会明显加分；再补一句"我用 4 条安全测试把这个边界锁住了"更完整。

### 2.2 补 7 个空壳路由 —— 注意外键陷阱

```

→ IntegrityError (1451, 'Cannot delete or update a parent row: a foreign key constraint fails ...')

information_schema 显示：fk_orders_customer  DELETE_RULE = NO ACTION
                          fk_orders_product   DELETE_RULE = NO ACTION
```

**所以「删除客户」这个按钮，只要该客户有订单，就一定会报错。** 这是你必然会踩到的坑，也是**绝佳的面试素材**。

三种解法，要能说出取舍：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 拦截提示 | 先 `SELECT COUNT(*) FROM orders WHERE customer_id=?`，>0 就提示 | 安全、业务友好 | 多一次查询 |

**强烈建议选「软删除」，并在面试里讲清理由**：电商订单是财务凭证，法律和审计上不允许物理删除；实际业务里客户"注销"只是标记状态，订单必须保留用于对账。

**RESTful 规范提醒**：HTML `<form>` 只支持 GET/POST。想用真 `DELETE` 需要 `fetch` 或 `method="post"` + 隐藏字段 `_method=DELETE`（Flask 需自己解析）。面试可能问「你怎么在只有 GET/POST 的浏览器里实现 RESTful」。

## 5. RFM 专业化 ★★ 这是面试的核心战场

> 面试官看到 RFM 项目，**一定会往深里问**。这部分投入产出比最高。

### 5.1 🔴 F 已改成「购买频次」，不再是「购买件数」✅

当前 `utils/rfm.py` 的 `rfm_table()` 聚合已经使用交易笔数：

```python
f=('transaction_id', 'count'),   # F 是消费频次（交易笔数），不是购买件数
```

**为什么这个区别重要**（面试必答）：

| 客户 | 表现 | 件数 | 频次 | 真实价值 |
|---|---|---|---|---|
| A | 一次买 100 件 | 100 | 1 | 可能是一次性大单 / 团购 |
| B | 买 100 次每次 1 件 | 100 | 100 | 高频复购，忠诚度高 |

如果用件数当 F，A 和 B 得分相同，但运营策略完全相反：A 需要观察是否复购，B 是核心忠诚客户。
因此 RFM 分层必须用**订单笔数**；购买件数可以保留为辅助指标，用于库存和物流视角。

**后续增强**：同时输出 `f_order_cnt` 与 `f_quantity`，页面分别标注「消费频次」和「购买件数」，
让业务能同时看到行为频次与采购规模。

### 5.2 R 的基准日：从「按年」演进到「观察窗口」

> **2026-10-19 现状**：代码已进一步演进成**观察窗口**口径 —— 基准日取数据集最新订单日，
> 窗口可选近 3 / 6 / 12 个月 / 全部（`utils/rfm.py` 的 `WINDOWS` + `rfm_table()`），先切窗口再排名分箱。
> 下面「按年取基准日」是中间版本，保留作为踩坑素材（尤其 `transform('max')` 那段）。

**中间版本（按年基准日）的实现**：

```python
orders_df['year'] = orders_df['order_date'].dt.year
orders_df['max_date'] = orders_df.groupby('year')['order_date'].transform('max')
orders_df['r_day'] = (orders_df['max_date'] - orders_df['order_date']).dt.days
```

含义：按年份取**该年最后一笔订单日期**作为 RFM 的分析基准日，而不是取整个数据集的最后日期。
否则 2023 年客户的 R 会被 2025 年的最后交易日拉大，早期年份的流失状态完全失真。

**⚠️ 这里有个真实踩坑，很适合面试讲**：必须用 `transform('max')`，不能用 `groupby('year')['order_date'].max()`。

| 写法 | 含义 | 结果 |
|---|---|---|
| `groupby().transform('max')` | 把每年最大日期广播回原 DataFrame 的每一行 | ✅ 正确 |
| `groupby().max()` | 返回压缩后的年度聚合表，索引是年份 | ❌ 赋回原表时索引对不上，全变 `NaT` |

一旦 `max_date` 全是 `NaT`，`r_day` 就全是 `NaN`，后面 `pd.qcut(rfm_df['r_day'], 3, ...)` 会直接报：

```
ValueError: Bin edges must be unique: Index([nan, nan, nan, nan])
```

**面试讲点**：这叫「观察窗口（observation window）」，RFM 必须先定义窗口和基准日才能算指标。
能讲清 `transform` 与普通 `groupby` 聚合的区别，比只说「我取了最大日期」更能体现实践。

### 5.3 分箱：`qcut` 的坑 ✅ 已落地

> **已落地（2026-10-19）**：`utils/rfm.py` 的 `_score_by_rank()` 已按本节结论改成
> `pd.qcut(values.rank(method='first'), k, labels=...)`，并处理了「客户数不足 3 个」的边界
> （`k = min(LEVELS, n)`，`k < 2` 时直接给最高档）。下面是原始分析与实测，留作面试素材。

改造前写法是 `pd.qcut(x, 3, labels=['3','2','1'])` 等频分箱。**实测结果**：

```
按年基准日后：812 个客户中有 177 个不同的 R 值 → 重复率约 78.2%

当前数据 qcut 直接跑：OK
但构造 R 值高度集中的数据：ValueError: Bin edges must be unique: Index([1.0, 1.0, 2.0, 5.0])
```

⚠️ 也就是说：改成年度基准日只让 R 的分布略有变化，**并没有消除重复边界风险**；换一份数据仍可能让 `/ge_rfm` 500。

**根因**：当分位点恰好落在重复值上（数据高度倾斜，比如大量客户都是「今天买过」），相邻箱边界会相等，`qcut` 直接抛错。

**我实测的四种修法**（重要，因为最常见的建议是错的）：

| 写法 | 结果 |
|---|---|
| `pd.qcut(x, 3, labels=lab)` | ❌ 重复边界时报错 |
| `pd.qcut(x, 3, labels=lab, duplicates='drop')` | ❌ **仍报错**：`Bin labels must be one fewer than the number of bin edges`（丢了一个边界，标签数对不上） |
| `pd.qcut(x.rank(method='first'), 3, labels=lab)` | ✅ **推荐**，rank 让所有值唯一，边界永不重复 |
| `pd.qcut(x, 3, labels=False, duplicates='drop')` | ✅ 可行，但箱数可能少于 3，要额外处理 |

> ⚠️ 注意：网上大量文章推荐 `duplicates='drop'`，**但在带 `labels` 时会报错**。这是个能体现你「亲自验证过」的细节。

**面试可能追问的对比**：

| 方法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| `qcut` 等频 | 按分位数切 | 每组人数均匀 | 相同值可能被分到不同组；重复边界报错 |
| `cut` 等距/自定义 | 按固定阈值切 | **业务可解释**（如 R: 7/30/90/180 天） | 可能某组人数为 0 |
| KMeans 聚类 | 数据驱动 | 捕捉真实分布 | 结果不稳定、需标准化、不可解释 |

**当前实测**（按年基准日后）：812 个客户中有 **177 个不同的 R 值**，重复率约 **78.2%**。
当前数据 `qcut` 直接跑能通过，但一旦 R 值更集中，仍会触发重复边界报错。

**建议（已采纳，代码见 `utils/rfm.py:67`）**：把 R/M 的 `qcut` 改成对 `rank(method='first')` 分箱，或改用业务阈值：
- R 用自定义阈值（业务含义清晰：「一周内 / 一月内 / 三月内 / 半年内 / 更久」）
- F 继续用 `cut` 自定义阈值
- M 可用等频，但同样建议加 `rank(method='first')` 防御

能说出「为什么 R 不用等频」就是加分项 —— 因为 R 的天数有天然业务分界点。

### 5.4 客户分层命名 ★ 最大的加分项

你现在是 `rfm_group` = 三档拼成的数字串（如 `321`），页面上就是个黑徽章。**纯数字对业务零意义。**

加上中文分层名称，面试官立刻知道你懂业务、不只是会拼字符串。

经典 8 分层（按 M 高低分「重要/一般」，按 R/F 高低分 4 类）：

| 分层 | R | F | M | 业务含义与策略 |
|---|---|---|---|---|
| **重要价值客户** | 高 | 高 | 高 | VIP，重点维护，专属服务 |
| **重要保持客户** | 低 | 高 | 高 | 曾高价值、近期流失 → **重点挽回** |
| **重要发展客户** | 高 | 低 | 高 | 近期大额但频次低 → 提升复购 |
| **重要挽留客户** | 低 | 低 | 高 | 大额但久未回且频次低 → **最危险** |
| **一般价值客户** | 高 | 高 | 低 | 活跃但客单价低 → 提客单价 |
| **一般保持客户** | 低 | 高 | 低 | 频次高但金额低、近期不来 |
| **一般发展客户** | 高 | 低 | 低 | 新客/低频，需培育 |
| **一般挽留客户** | 低 | 低 | 低 | 流失客户，低成本触达 |

实现就是一个映射函数：
```python
def segment(r, f, m):
    r_hi, f_hi, m_hi = r >= 2, f >= 2, m >= 2
    ...
```
页面上加一列彩色标签，按分层给不同颜色。

**面试怎么讲**：从「27 个数字分组」到「8 类业务分层」的转换，是**数据 → 洞察 → 行动**的完整链路。业务方看不懂 `321`，但看得懂「重要保持客户，建议发召回券」。

## 6. 性能与工程化

### 6.1 物化 RFM 结果表 ★

**现状**：每次打开 `/ge_RFM` 都 `SELECT * FROM orders`（全表）→ 拉回 pandas → 全量 groupby + qcut + merge。

| 数据量 | 后果 |
|---|---|
| 2000 行（现在） | 约 100–300 ms，能忍 |
| 30 万行 | 每次请求数秒，几个并发就拖垮 |
| 300 万行 | 内存爆 + 请求超时 |

**改法**：导入完成后（`/clear_input` 里）**预计算** RFM 结果，写入 `rfm_result` 表：

```sql
CREATE TABLE rfm_result (
  customer_id VARCHAR(64),
  window_key  VARCHAR(8),          -- 与页面下拉一致：3m / 6m / 12m / all
  r INT, f INT, m DECIMAL(12,2),
  r_level TINYINT, f_level TINYINT, m_level TINYINT,
  segment VARCHAR(32),
  PRIMARY KEY (customer_id, window_key)
) ENGINE=InnoDB;
```

页面直接 `SELECT ... FROM rfm_result WHERE window_key=? LIMIT ? OFFSET ?`。

> 💡 你的 MySQL 里已经有一个 `rfm_db.rfm_table`（19.9 MB）—— 说明你之前做过类似的物化表。这次把它放进主项目里，并在面试中讲清楚。

**面试讲点（很高级）**：
- **离线计算 vs 实时计算**的权衡：RFM 是典型的 T+1 批处理场景，不需要实时
- **空间换时间**：多存一张表，换页面响应从秒级到毫秒级
- **计算时机**：导入后算 vs 定时任务算 vs 触发式算
- 如果数据量再大：MySQL 里用窗口函数直接算完（`NTILE(3) OVER (ORDER BY r)`），不用拉进 Python —— **顺便展示你会写窗口函数**

### 6.2 分页改成后端分页

**现状**：4 个列表页各自复制了约 65 行**完全相同**的 JS，而且是**伪分页** —— 后端把全部行渲染进 DOM，前端 `display:none` 隐藏。

| 数据量 | DOM 节点数 | 后果 |
|---|---|---|
| 2000 行 | 约 2 万个 `<td>` | 卡顿半秒 |
| 30 万行 | 300 万个 | **浏览器直接崩** |

**改法**：
1. 后端 `LIMIT / OFFSET`，只传当前页
2. 把 4 份重复 JS 抽成 `static/js/pagination.js`
3. 列表页模板用 `{% include %}` 复用

**面试讲点**：`LIMIT/OFFSET` 在深分页时性能差（`OFFSET 100000` 要扫描并丢弃 10 万行），优化手段是**游标分页**（`WHERE id > 上次最后一个 id LIMIT 20`）。能主动提到这点很加分。
