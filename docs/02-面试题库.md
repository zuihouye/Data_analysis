### Q2. 🔴 为什么选 Flask 不用 Django / FastAPI？

**标准的错误答法**：「Flask 简单 / 我只会 Flask」→ 减分。

**加分答法（三层）**：
1. **Flask**：轻量、灵活，适合这种「数据分析 + 少量页面」的场景，不需要 Django 的 ORM/Admin/认证全家桶。
2. **对比 Django**：Django 是「重框架」，自带 ORM、Admin、Auth、迁移，适合业务 CRUD 密集型项目。我这个项目核心是 pandas 数据处理，Django 的 ORM 反而绕（我要跑复杂聚合），所以不用。
3. **对比 FastAPI**：FastAPI 异步、自动生成 OpenAPI 文档、性能更好，适合纯 API 服务。但我需要服务端渲染 HTML 页面，Flask 的 Jinja2 更直接，而 FastAPI 一般配前后端分离。

💡 **主动补一句**：「如果这个项目要拆成前后端分离、给移动端提供 API，我会选 FastAPI。」

> 面试官问框架选型，考的不是你「会哪个」，而是**你能不能说清权衡**。

### Q3. 🔴 RFM 模型是什么？R / F / M 分别怎么算？

- **R（Recency）**：最近一次消费距**基准日**的天数，**越小越好**
- **F（Frequency）**：观察窗口内的消费频次（**订单笔数**），越大越好
- **M（Monetary）**：观察窗口内的消费总金额，越大越好

⚠️ **必须主动说「观察窗口」**：
> 「算 RFM 之前必须先定义观察窗口和基准日。我的基准日取**数据集里最新的订单日**（不是 `today`），
> 窗口可以切「近 3 / 6 / 12 个月 / 全部」。关键是**先切窗口、再在窗口内排名分箱** —— 顺序反了得到的是
> "全量排名的一个子集"，实测近 3 个月窗口下 93.5% 的客户分组会被改写。」

实现上是先按 `order_date > snapshot - offset` 过滤窗口，再求 R：

```python
orders = orders[orders['order_date'] > snapshot - offset]      # 先切窗口
orders['r_day'] = (snapshot - orders['order_date']).dt.days    # 再算 R
```

💡 **早期版本踩过的坑（可以讲）**：最早我按 `(customer_id, year)` 分组、用
`groupby('year')['order_date'].transform('max')` 取年度基准日；写成 `groupby('year').max()`
时返回的是压缩后的聚合表、索引对不上，`max_date` 全变 `NaT`，随后 `qcut` 直接报
`Bin edges must be unique`。后来发现按年分组本身也不够灵活（跨年窗口算不了），
才改成"观察窗口 + 数据集最新日"的口径。

### Q5. 🔴 分箱为什么选 3 档？`qcut` 和 `cut` 的区别？

| | `qcut` 等频 | `cut` 等距 / 自定义 |
|---|---|---|
| 原理 | 按分位数切，每组人数≈相等 | 按固定阈值切 |
| 优点 | 组间人数均衡 | **业务可解释** |
| 缺点 | 相同值可能被分到不同组 | 可能某组为空 |

**答 3 档的原因**：3×3×3=27 组；再按 R/F/M 高低二值化就能收敛成 8 类业务分层（**已落地**：每维 3 档折「高/低」，3 = 高、1/2 = 低，页面同时给出 27 种组合码和 8 个中文分群，见 `utils/rfm.py` 的 `SEGMENTS` / `segment_of`）。业界也有用 5 档的，区分度更高但边际收益递减。

💡 **主动补充**：
> 「其实 R 我更倾向用**自定义阈值**而不是等频，因为天数的业务分界点是天然的 —— 比如「7 天内 / 30 天内 / 90 天内 / 半年内」。用等频会把「都是昨天买过」的客户强行切开，业务上没意义。」

### Q6. ⚠️🔴 `qcut` 遇到大量重复值会怎样？怎么解决？

**这是最能体现「你亲自踩过坑」的一题。**

- **现象**：`ValueError: Bin edges must be unique`
- **根因**：分位点落在重复值上（数据高度倾斜，如大量客户都是「今天买过」），相邻箱边界相等
- **数据佐证**：812 个客户里 R 值大量重复（很多客户最后一次购买在同一天），重复高度集中；直接 `qcut` 随时可能踩到重复边界

**修法对比（这里有个反直觉的点，答对非常加分）**：

| 写法 | 结果 |
|---|---|
| `qcut(x, 3, labels=lab)` | ❌ 重复边界报错 |
| `qcut(x, 3, labels=lab, duplicates='drop')` | ❌ **仍然报错**：`Bin labels must be one fewer than the number of bin edges` |
| `qcut(x.rank(method='first'), 3, labels=lab)` | ✅ 推荐：rank 让值唯一，边界永不重复 |
| `qcut(x, 3, labels=False, duplicates='drop')` | ✅ 可行，但箱数可能 < 3 |

💡 **主动说**：「网上大部分文章推荐 `duplicates='drop'`，**但它在带 `labels` 参数时会报错**，因为丢掉一个边界后标签数量对不上了。我的防御方案是在 `utils/rfm.py` 里先对 `x.rank(method='first')` 打散再做 `qcut`，rank 让值唯一、边界永不重复；顺带处理了客户数不足 3 个、切不出 3 档的边界（`k = min(3, n)`）。」

> 这一句「我实测后发现网上答案是错的」杀伤力极强。

### Q7. 🔴 数据清洗你都做了哪些？怎么保证质量？

按「查什么 → 怎么查 → 发现问题怎么办」组织：

| 检查项 | 手段 | 处理策略 |
|---|---|---|
| 日期格式 | `pd.to_datetime(format=...)` | 格式不符抛错，不静默 |
| 金额千分位 | `str.replace(',','')` | 数据集里是 `"25,000"` |
| 空值 | `dropna()` | 丢弃并记录数量 |
| 主键重复 | `duplicated()` | 交易号重复会让唯一键冲突，整批失败 |
| **金额一致性** | `np.isclose(amount, qty*ppu)` | 数据集 README 明确要求校验 |
| 客户-地区一对多 | `groupby().nunique() > 1` | 保留首个 **+ 打警告日志**，不静默 |

💡 **核心观点（一定要说）**：
> 「清洗遇到冲突有四种策略 —— 静默丢弃、保留首个并告警、人工介入、直接失败。**选哪种取决于业务后果。** 我的原则是「**不静默**」：可以丢，但必须留下日志和统计，否则数据问题会被埋掉。」

💡 **浮点**：金额比较必须用 `np.isclose` 而不是 `==`，因为 `0.1+0.2 != 0.3`。数据库用 `DECIMAL` 存储而不是 `FLOAT` 也是同一个原因。

### Q8. 🔴🔴 你的数据导入失败了会怎样？事务是怎么设计的？

**这是你最强的技术故事，务必讲透。**

按「原来的错误做法 → 为什么错 → 怎么发现 → 怎么改 → 额外收益」组织：

**原来的做法**（`utils/db.py`）：
```python
with engine.begin() as conn:              # 看起来有事务
    conn.execute(text("TRUNCATE TABLE orders;"))
    ...
customers_df.to_sql('customers', engine, ...)   # 块外，新连接
```

**两个问题**：
1. **`TRUNCATE` 是 DDL，会强制隐式提交**，`with engine.begin()` 根本回滚不了它
2. **`to_sql` 传 `engine` 时自己借连接、自己提交**，三条 `to_sql` 各自独立

**怎么发现的**：我写了个验证脚本，插入 3 行 → 在事务里 `TRUNCATE` → 抛异常触发回滚 → **剩余 0 行**（对照组 `DELETE` 回滚后剩余 3 行）。这就证实了 `TRUNCATE` 不可回滚。

**净效果**：导入中途失败 → **三张表已被清空且无回滚**，页面全空。

**已落地的改法**：单事务 `DELETE + INSERT`（只用 DML）

```python
with (db_engine or db.engine).begin() as conn:
    for table in ('orders', 'customers', 'products'):
        conn.execute(text(f'DELETE FROM {table}'))
    customers_df.to_sql('customers', conn, if_exists='append', index=False)
    products_df.to_sql('products', conn, if_exists='append', index=False)
    orders_df.to_sql('orders', conn, if_exists='append', index=False)
```

核心点：
1. 不用 `TRUNCATE` / `CREATE` / `RENAME`，因为它们是 DDL，会隐式提交
2. `to_sql` 传 `Connection`，纳入外层事务，不自己提交
3. 删除顺序是子表 → 父表，写入顺序是父表 → 子表，因此不需要关闭外键检查
4. 失败时事务完整回滚，有 `test_failure_inside_transaction_rolls_back` 锁住

💡 **如果面试官问“要不要不停机”**：再讲临时表 + `RENAME TABLE` 原子切换方案。
但要主动说明：`RENAME` 也是 DDL，不能靠外层事务回滚，它的保证是“正式表要么全不变，要么被原子换掉”。
当前 2000～30000 行规模下，DELETE 是毫秒级，没必要引入复杂度。

> 这个故事包含了：**框架误用 → 主动验证 → 方案权衡 → 最终选择**。比背八股强十倍。

### Q9. 🔴 `TRUNCATE` / `DELETE` / `DROP` 的区别？

| | TRUNCATE | DELETE | DROP |
|---|---|---|---|
| 类型 | DDL | DML | DDL |
| 能否回滚 | ❌ 隐式提交 | ✅ | ❌ |
| 是否走 `WHERE` | ❌ 全表 | ✅ | ❌ |
| 重置 `AUTO_INCREMENT` | ✅ | ❌ | — |

| 速度 | 快（按页释放） | 慢（逐行 + 写 undo/redo） | 快 |
| 表结构 | 保留 | 保留 | **删除** |

### Q10. 🔴 为什么删除客户会失败？

**实测证据**：
```
DELETE FROM customers WHERE customer_id='Customer-002'
→ IntegrityError (1451, 'Cannot delete or update a parent row: a foreign key constraint fails')
```

`orders` 表有两个外键指向 `customers` / `products`，`DELETE_RULE = NO ACTION`（等价于 RESTRICT），所以**只要该客户有订单就删不掉**。

**三种解法与取舍**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 拦截提示 | 先查 `COUNT(*)` 再决定 | 安全、友好 | 多一次查询 |
| **软删除** ✅ | 复用业务状态列（`cus_status` / `product_status`），不是新增 `is_deleted` | 可恢复、保留历史、语义不重复 | 要区分"业务状态"和"删除状态" |
| 级联删除 | `ON DELETE CASCADE` | 代码简单 | **危险**，删客户连带删光订单 |

💡 **推荐答法**：
> 「电商订单是财务凭证，法律和审计上不允许物理删除。所以正确做法是**软删除** —— 客户「注销」只是标记状态，订单必须保留用于对账。实际项目里我还会加一个「客户注销」的业务流程，而不是一个删除按钮。」

**本项目已落地（P2，2026-10-20）**：
- 客户「删除」= `cus_status=2` + 关联账号 `users.is_active=2`，订单一条不删（有测试断言行还在）；
- 商品「删除」= `product_status=2` 下架；订单「删除」= `order_status=3` 取消（条件 `UPDATE` + `rowcount`）；
- **软删除之后的真坑**：CSV 全量重灌会 `DELETE` 三张表，把注册客户的账号一起冲掉 → 在 `write_to_db` 的 `DELETE` 之前加 `ensure_import_safe()`，检测到"业务数据"就拒绝并 409。能讲出这一层，比只背"软删除"高一个身位。

### Q11. ⚠️🔴 为什么「导入数据」不能用 GET？你现在是怎么处理的？

**为什么 GET 是严重问题**：
1. **违反 HTTP 语义**：GET 必须是 **safe**（不改变服务端状态）且 **idempotent**
2. **会被误触发**：浏览器预取（prefetch）、爬虫、安全扫描器都可能发出 GET，**直接清库**
3. **难以防 CSRF**：GET 可以被 `<img src="http://你的站点/clear_input">` 跨站触发
4. **无鉴权**：任何人知道 URL 就能清库

**已落地的修复（分两步）**：
1. `@ci_blue.route('/clear_input', methods=['POST'])`；导航栏由 `<a href>` 改成 `<form method="post">`；测试同步改 `.post()`
2. **认证 + 授权 + CSRF**：`@admin_required` 装饰器（未登录 302 跳 `/login?next=...`，非管理员 403）、
   `before_app_request` 对所有写方法统一校验 CSRF token、登录页不再让用户自选身份

**仍可加强**：前端二次确认、操作审计日志。

💡 **推荐回答**：
> 「这个接口名叫「导入数据」，但它实际做的是**全表清空重灌**，破坏性极强，本质是运维操作。
> 我分两步收口：先把 GET 改成 POST，消除误触发和违反 HTTP 语义的问题；再加上认证、授权和 CSRF ——
> 未登录跳登录页，只有管理员能触发，所有写请求都校验 CSRF token。
> 我又补了 4 条安全测试把这个边界锁住。」

### Q12. 🔴 你的项目有多少数据量？大了会怎样？怎么优化？

**诚实分层回答**：

| 数据量 | 现状的后果 |
|---|---|
| 2000 行（当前） | 响应 100–300 ms，可用 |
| 30 万行 | 每次请求秒级 + 页面卡死（前端伪分页渲染 300 万 DOM 节点） |
| 300 万行 | 内存爆 + 超时 |

**两个优化方向**：

**① 物化 RFM 结果表（离线计算）**
```sql
CREATE TABLE rfm_result (
  customer_id VARCHAR(64), window_key VARCHAR(8),   -- 3m / 6m / 12m / all
  r INT, f INT, m DECIMAL(12,2),
  r_level TINYINT, f_level TINYINT, m_level TINYINT,
  segment VARCHAR(32),
  PRIMARY KEY (customer_id, window_key)
);
```
导入后预计算，页面直接查表。**空间换时间**。

💡 **加分**：「RFM 是典型的 T+1 批处理场景，不需要实时。如果数据量再大，我甚至可以不拉到 Python —— 直接在 MySQL 里用窗口函数 `NTILE(3) OVER (ORDER BY r_day)` 算完，减少数据传输。」

**② 后端分页**
现在是「后端全量渲染 + 前端 `display:none` 隐藏」的**伪分页**。
改成 `LIMIT/OFFSET`。💡 再补：「但 `LIMIT/OFFSET` 在深分页时也慢（`OFFSET 100000` 要扫描并丢弃 10 万行），更好的方案是**游标分页**：`WHERE id > 上次最后一条的 id LIMIT 20`，配合索引可以做到 O(1)。」

### Q13. 🔴 项目里最难的问题是什么？怎么解决的？

**别答「没什么难的」**。用 STAR 结构准备 2–3 个，首选 Q8（事务原子性），备选 Q6（qcut）或 Q10（外键）。

### Q14. 🔴 如果让你重新设计，你会改什么？

按优先级答 3–4 个，别贪多：
1. **权限模型细化** —— 现在只有「普通成员 / 管理员」两级；真实业务需要按操作（导入 / 删除 / 看金额）细粒度授权，并加操作审计日志

### Q15. 项目里怎么防 SQL 注入？

- 好消息：`pd.read_sql(sql, con=engine)` 里没拼用户输入，全是常量 SQL

### Q16. 你的连接池怎么配的？为什么？

现在：`pool_size=30, max_overflow=20, pool_timeout=30, pool_recycle=3600, pool_pre_ping=True`

**逐项解释**（能全部说清很加分）：
- `pool_size=30`：常驻连接数。**但对一个单机小项目来说 30 偏大** —— 每个 MySQL 连接约占几 MB 内存，且 `max_connections=100`（你 `my.ini` 里的配置），30+20=50 已经占了一半。单机小项目 5–10 就够。
- `max_overflow=20`：池满时最多再临时创建 20 个
- `pool_recycle=3600`：**连接超过 1 小时就回收**。因为 MySQL 默认 `wait_timeout=8h`（你配的是 120 秒！），连接空闲太久会被服务端单方面断开，客户端再拿这个"死连接"用就会报 `MySQL server has gone away`。所以 recycle 要**小于**服务端的 `wait_timeout`。
- `pool_pre_ping=True`：取连接前先 ping 一下，失效就换一个。这是防"死连接"最省心的手段。

⚠️ **注意一个真实隐患**：你的 `my.ini` 里 `wait_timeout=120`（2 分钟！），而 `pool_recycle=3600`（1 小时）。**recycle 远大于服务端的 wait_timeout**，所以理论上连接会被服务端先掐断。目前靠 `pool_pre_ping=True` 兜住了。**能指出这一点非常加分** —— 说明你真的读过配置。

## 二、Python 基础（🔴 八股，面试必问）

| # | 问题 | 关键点 |
|---|---|---|
| 1 | 可变 vs 不可变类型 | `list/dict/set` 可变；`int/str/tuple` 不可变。函数传参是「传对象引用」，可变对象在函数内修改会影响外部 |
| 2 | `is` vs `==` | `is` 比身份（`id()`），`==` 比值。小整数缓存 `-5~256`。**别用 `is` 比字符串** |
| 3 | 深拷贝 vs 浅拷贝 | `copy.copy` 只复制第一层；`copy.deepcopy` 递归。嵌套结构必须深拷贝 |
| 4 | 🔴 装饰器原理 | 本质是「接收函数、返回函数」的高阶函数。`@login_required` 就是。**必答 `functools.wraps` 的作用**：保留 `__name__`/`__doc__`，否则 Flask 多个视图都叫 `wrapper` 会 `Endpoint name collision`。**你会这个坑可以现场演示** |
| 5 | 🔴 生成器 / `yield` | 惰性求值、省内存。`yield` 把函数变成生成器，每次调用 `next()` 才执行到下个 `yield`。**处理大 CSV 时用 `pd.read_csv(chunksize=...)` 就是同一思想** |
| 6 | 🔴 `with` 上下文管理器 | `__enter__` / `__exit__`。`__exit__` 返回 `True` 会吞掉异常。**你的 `with engine.begin()` 就是它** —— 可以说「我用它管理数据库连接和事务」 |
| 7 | `*args` / `**kwargs` | 位置参数元组 / 关键字参数字典。装饰器里必用 |
| 8 | 🔴 GIL | 全局解释器锁，同一时刻只有一个线程执行 Python 字节码。**I/O 密集多线程有效（等待时释放 GIL），CPU 密集要用多进程**。你的 Flask 项目是 I/O 密集（等数据库），所以多线程有用；如果 RFM 计算是瓶颈，就该用多进程或把计算推给数据库 |
| 9 | 列表推导 vs 生成器表达式 | `[...]` 立即构造列表；`(...)` 惰性。大数据量用后者 |
| 10 | 闭包 & late binding | 闭包捕获变量而非值。`[lambda: i for i in range(3)]` 全部返回 2，要 `lambda i=i: i` |
| 11 | `__new__` vs `__init__` | `__new__` 创建实例（返回对象），`__init__` 初始化。单例模式用 `__new__` |
| 12 | 异常处理 | `try/except/else/finally`，`else` 是没异常时执行，`finally` 一定执行。**`except` 要具体，别裸 `except:`** |
| 13 | 垃圾回收 | 引用计数为主 + 标记清除 + 分代回收。**循环引用要靠后者** |
| 14 | 深浅拷贝在 pandas 里的体现 | `SettingWithCopyWarning` 就是链式索引导致的视图/副本歧义 |
| 15 | 单例模式实现 | 模块级变量 / `__new__` / 装饰器 / 元类。**你的 `engine` 就是模块级单例** |

## 三、MySQL / 数据库（🔴 高频）

| # | 问题 | 关键点 |
|---|---|---|
| 1 | 🔴 索引为什么用 B+ 树 | B+ 树矮胖（3–4 层可存千万级）、叶子节点连成链表适合**范围查询**；B 树非叶节点也存数据，同样高度存得更少；哈希索引不支持范围查询和排序 |
| 2 | 🔴 聚簇 vs 非聚簇索引 | InnoDB 主键是聚簇索引（叶子节点存整行）；二级索引叶子存主键值，查非索引列要**回表**。所以**主键要短**、**尽量覆盖索引避免回表** |
| 3 | 覆盖索引 | 查询的列都在索引里，不用回表。`EXPLAIN` 的 `Extra` 显示 `Using index` |
| 4 | 🔴 最左前缀原则 | 联合索引 `(a,b,c)` 能命中 `a`、`a,b`、`a,b,c`；不能只命中 `b` |
| 5 | 🔴 事务 ACID | 原子性（undo log）/ 一致性 / 隔离性（MVCC + 锁）/ 持久性（redo log） |
| 6 | 🔴 隔离级别 | 读未提交 / 读已提交 / **可重复读（MySQL 默认）** / 串行化。对应解决脏读、不可重复读、幻读。**MySQL 的 RR 靠 MVCC + 间隙锁基本解决了幻读** |
| 7 | MVCC | 版本链 + `ReadView`。`undo log` 存旧版本，读操作读快照 |
| 8 | 🔴 锁 | 行锁（InnoDB 默认）、表锁、间隙锁（防幻读）、意向锁。**没有索引的 `UPDATE` 会退化成表锁** |
| 9 | 🔴 死锁怎么排查 | `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`。预防：**按固定顺序访问资源**、缩短事务、加合适索引 |
| 10 | 🔴 `EXPLAIN` 看什么 | `type`（至少要 `range`，`ALL` 是全表扫描要优化）、`key`（实际用的索引）、`rows`（扫描行数）、`Extra`（`Using filesort`/`Using temporary` 要警惕） |
| 11 | 慢查询优化思路 | 加索引 → 避免 `SELECT *` → 避免在索引列上做函数运算 → 分页优化 → 读写分离/分库分表 |
| 12 | 🔴 三大范式 | 1NF 列不可再分；2NF 消除部分依赖；3NF 消除传递依赖。**实际项目常反范式**（如你 `orders` 存 `ppu` 快照就是有意冗余） |
| 13 | 🔴 你的 `orders` 为什么 `order_id` 和 `transaction_id` 分开？ | **这是个好设计，要主动讲**：`order_id` 是内部自增代理键（短、稳定、适合做外键和聚簇索引）；`transaction_id` 是业务流水号（有业务含义但要防伪造、可能变更）。**业务键和代理键分离**是标准实践 |
| 14 | 🔴 为什么 `orders` 要存 `ppu` 快照？ | `products.ppu` 是**当前单价**，会随时间改价。订单必须记录**交易发生时的实际单价**，否则历史订单金额会跟着商品调价而"漂移"，财务对账就错了。**这是数据仓库「事实表存快照」的思想** |
| 15 | 🔴 连接池为什么需要 | 建立 TCP + 认证很贵（几十 ms）。池化复用，避免频繁握手；同时**限制并发连接数**保护数据库 |
| 16 | 索引是不是越多越好 | 不是。索引占空间，且 `INSERT/UPDATE/DELETE` 都要维护索引，降低写性能 |
| 17 | `UNIQUE` 和 `PRIMARY KEY` 区别 | 主键非空且唯一、每表一个；唯一键允许 NULL、可有多个 |
| 18 | `VARCHAR` vs `CHAR` | `VARCHAR` 变长省空间；`CHAR` 定长，适合固定长度（如 MD5、性别） |

## 四、Flask / Web

| # | 问题 | 关键点 |
|---|---|---|
| 1 | 🔴 Flask 请求生命周期 | WSGI Server → `Flask.__call__` → 创建请求上下文 → `before_request` → 路由分发（Werkzeug 的 URL Map）→ 视图函数 → `after_request` → 响应。异常走 `errorhandler` |
| 2 | 蓝图的作用 | 模块化拆分路由，避免单文件臃肿；可统一加 `url_prefix`、`before_request`。你的项目 4 个蓝图 |
| 3 | 🔴 请求上下文 vs 应用上下文 | `request`/`session` 属于请求上下文（每个请求独立）；`current_app`/`g` 属于应用上下文。**为什么需要**：Flask 用「上下文栈 + 线程局部变量」（`contextvars`）实现，让 `request` 这种全局对象在多线程下互不干扰 |
| 4 | `g` vs `session` | `g` 只活在单次请求内、服务端内存；`session` 跨请求、默认存在客户端 Cookie（签名防篡改） |
| 5 | 🔴 Jinja2 怎么防 XSS | **默认自动转义**（`{{ }}` 会转义 HTML）。用 `|safe` 或 `Markup` 才不转义，**这是危险操作**。你模板里没有用 `|safe`，是安全的 |
| 6 | 🔴 CSRF 是什么，怎么防 | 攻击者诱导已登录用户发起非预期请求。防护：CSRF Token（`Flask-WTF` 的 `CSRFProtect`）、`SameSite` Cookie、校验 `Referer` |
| 7 | 生产环境怎么部署 | **不能用 `app.run()`**（开发服务器单线程、性能差、有安全提示）。用 `gunicorn`（Linux）/ `waitress`（Windows）多 worker + Nginx 反代 + 静态文件交给 Nginx |
| 8 | Flask 怎么处理并发 | 默认开发服务器是单线程；生产用 gunicorn 多进程。**每个进程独立**，所以不要用进程内全局变量存状态（应该用 Redis） |
| 9 | `url_for` 的好处 | 反向解析 URL，改路由不用改模板；自动处理蓝图前缀和特殊字符转义 |
| 10 | 中间件怎么做 | `before_request` / `after_request` / `teardown_request`；或 WSGI 中间件 |
| 11 | 跨域 CORS | 浏览器的同源策略。服务端返回 `Access-Control-Allow-Origin`。`flask-cors` 扩展 |

| # | 问题 | 关键点 |
|---|---|---|
| 1 | `apply` / `map` / `applymap` | `map` 只对 Series 逐元素；`apply` 可对 Series 或 DataFrame 按行/列；`applymap`（新版 `map`）对 DataFrame 逐元素。**性能都不如向量化** |
