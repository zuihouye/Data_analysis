# 缺陷复盘模板（Bug Retrospective）

> 用法：每发现一个"值得写进简历/面试讲"的 bug，复制下面模板填一份，文件名建议 `BUG-编号-一句话现象.md`。
> 一份好的复盘不是"我改了哪里"，而是"别人看完能自己定位同类问题"。
> **正文全部由你自己写**；下面只给结构和写作要求。

---

## 一、基本信息

| 项目 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-001 |
| 发现日期 | 2026-XX-XX |
| 发现人 | 你的名字 |
| 所属模块 | 登录 / 商品 / 订单 / 支付 / 权限 / 环境 |
| 严重级别 | 致命 / 严重 / 一般 / 轻微（参考：能否阻断主流程、是否影响数据正确性） |
| 优先级 | P0 / P1 / P2 / P3 |
| 状态 | 新建 / 已修复 / 已回归 / 关闭 |
| 关联用例 | 如 LG-15、PD-23（对应 `用例集-模板.csv` 的编号） |

## 二、现象（用户视角）

- 操作步骤：
  1. 打开 `/xxx`
  2. 点击/提交 `...`
- 实际结果：`HTTP 状态码 + 页面提示 + 是否产生脏数据`
- 期望结果：`业务上应该发生什么`

> 写法要求：能复现、能看懂。不要写"功能不对"，要写"点登录后停在原页，提示 401"。

## 三、复现与最小化

- 复现概率：必现 / 偶现（几次中几次）
- 最小复现条件：`哪个账号 + 哪条数据 + 哪个参数`
- 环境：Python 版本、Flask 版本、数据库/Redis 版本、浏览器版本（环境问题尤其要写）

## 四、定位过程（这是复盘最值钱的部分）

按时间顺序写"我做了什么假设 → 怎么验证 → 结果如何"：

1. 先看 HTTP 状态码 / 响应体，判断是前端问题还是服务端问题；
2. 打开浏览器 F12 → Network / Console，确认请求是否发出、参数对不对；
3. 对照源码找到入口函数，看分支条件；
4. 需要时加一行日志/print，或直接用 `pytest` 单测复现；
5. 确认是代码 bug、设计差异，还是环境问题。

> 面试讲法：面试官不关心你改了几行，关心你"怎么想到去看那里的"。

## 五、根因

- 直接原因：`代码里的哪一行/哪个判断导致了这个结果`
- 深层原因：需求没写清 / 接口契约不一致 / 异常分支漏了 / 版本不兼容 / 测试环境与生产不一致……
- 为什么之前没发现：没有对应用例 / 用例只测 happy path / 数据没覆盖到

## 六、修复

- 修改文件与位置：`文件:行号`
- 修改思路：`加判断 / 调整状态码 / 修正提示文案 / 改依赖版本`
- 是否影响其他功能：`会影响哪些页面/接口，如何确认`
- 代码提交/PR：`链接或 commit 号`

## 七、回归验证

- 新增/补充的用例编号：`LG-09`（`用例集-模板.csv`）
- 自动化脚本：新增到 `qa/api/test_login.py::test_xxx`，并说明断言点
- 验证结果：`pytest qa\\api -v` → `N passed`
- 是否需要数据修复：`是/否，SQL 或手动步骤`

## 八、预防措施（一句话即可）

- 格式要求：写"之后所有同类问题都不会再犯"的那一条动作（用例、规范、依赖锁、CI 门禁）。

# 附录：三个可以写的案例（只给线索，正文你来写）

这三条都是这个项目里真实存在的现象，你按上面的模板各写一份，写完发我批。

## 案例 A：登录接口一直失败（数据层）

- 线索：打开 `E:\Flask_app\views\auth.py`，找到登录时那条 `SELECT`；再去数据库里看 customers 表的真实列名，两者比对一下。
- 你要写的：现象（用户看到什么）→ 怎么定位到的 → 根因 → 修复 → 补了哪条用例。

## 案例 B：登录成功后 session 写入报错（框架层）

- 线索：`_save_login` 里对查询结果调用了某个字典方法；SQLAlchemy 2.x 查询返回的 `Row` 对象是什么？它支持哪些访问方式？
- 你要写的：同 A。

## 案例 C：查询不存在的商品返回 302 而不是 404（设计差异）

- 线索：页面型项目（服务端渲染 + flash）和 JSON 接口对"资源不存在"的表达方式不同；看 `views/order.py` 里商品读取那段是 302 还是 404，再想想 `/pay/order/<id>` 那类 JSON 接口会怎么返回。
- 你要写的：同 A，并在结尾回答"这算不算 bug"。
